# AI WealthPilot web rules

The block above is generated by Next.js. Do not edit or remove it manually. Project-specific rules live below this line.

## Data access boundaries

- Read-only data needed during server rendering should use `src/lib/api/` domain modules. Keep the API client split by domain and re-export through the existing barrel where appropriate.
- Browser-originated mutations, uploads, long-running task creation, SSE/streaming, and other requests that need same-origin behavior must go through `src/app/api/` proxy routes and the helpers in `src/lib/proxy.ts`.
- Do not expose backend-only origins, credentials, API keys, or internal network addresses to client components or browser bundles.
- Keep financial/domain calculations on the Python side. The Web app may format, visualize and collect inputs, but it should not duplicate portfolio, risk, IPS or retirement logic from `src/`.

## i18n

- User-visible UI copy belongs in `src/lib/i18n/dictionaries/{en,zh}/`; new or changed copy must keep both dictionaries structurally aligned.
- Server components should use the existing server-side dictionary helpers; client components should use the existing locale context/hooks instead of introducing a second i18n mechanism.
- Same-origin proxy helpers are responsible for propagating locale to FastAPI. For server-side direct API calls that need localized backend text, pass locale explicitly rather than importing `next/headers` into shared client modules.
- Do not hard-code new Chinese or English UI strings in components when the text is visible to users and should switch with locale.

## Design system

- Reuse primitives from `src/components/ui/` before adding one-off buttons, panels, tables, chips, icons or state widgets.
- Theme and semantic tokens live in `src/app/globals.css`. Prefer semantic tokens over raw Tailwind color families or ad-hoc hex values.
- Directional market performance must use the semantic rise/fall tokens so English and Chinese locales can apply their respective color conventions. Do not encode “up = jade/green” or “down = cinnabar/red” directly in feature components.
- Use the project icon system in `src/components/ui/icon.tsx` rather than emoji as UI icons.
- Plotly output should render through `src/components/plot-chart.tsx` so theme behavior stays centralized.

## Component and route discipline

- Prefer small server pages that assemble reusable client workspaces/components; avoid moving an entire route to the client just because one section is interactive.
- Keep API proxy route handlers thin. Validation and transport adaptation are fine; business rules belong in the backend.
- Reuse existing SSE/task-resume helpers for long-running flows instead of implementing a second event parser or reconnection protocol in a component.
- Preserve accessible labels, keyboard behavior, loading states, empty states and error states when modifying forms or workspaces.

## Validation

Run the smallest relevant checks first, then expand based on impact:

```bash
npm test
npm run typecheck
npm run lint
npm run build
```

- Component or shared-lib changes should normally add or update Vitest/Testing Library coverage near the changed module.
- Proxy, SSE, locale, async task-resume or cross-page workflow changes should also run the relevant Playwright tests; for broad user-flow changes run `npm run test:e2e`.
- `npm run build` is not a substitute for `npm run typecheck`; test files are part of the TypeScript surface even when Next build does not exercise them.
